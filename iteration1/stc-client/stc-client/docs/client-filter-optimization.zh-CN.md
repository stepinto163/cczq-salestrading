# 客户端组合筛选首轮优化（2026-10-09）

## 结果

在相同的本机 500 条报价、单 STC 客户端、两组组合条件、开启行列虚拟化的基准中，点击筛选端到端 p95 从 **404.77 ms 降至 96.24 ms**，降低约 76%。本轮点击路径达到 100 ms 参考目标；20 个样本的最大值仍为 116.42 ms，不代表每次均小于 100 ms，也不代表 QA 网络或并发负载已达标。

|阶段（p95）|优化前|仅优化 codec|再优化管理页集合更新|
|---|---:|---:|---:|
|点击筛选到渲染|404.77 ms|261.56 ms|96.24 ms|
|自动筛选到渲染|743.00 ms|542.09 ms|400.49 ms|
|view.open 协议解码|132.04 ms|8.91 ms|9.71 ms|
|DTO 转回 JSON|50.09 ms|8.28 ms|7.67 ms|
|管理页集合更新|30.46 ms|40.52 ms|15.56 ms|
|等待 Render 优先级观察点|146.41 ms|145.18 ms|20.13 ms|

各阶段 p95 不可直接相加。优化前为[详细剖析轮](client-response-profile.zh-CN.md)，三轮顺序执行，工作负载未增加。存在正常运行波动，尤其不同轮的集合耗时不能单独归因于 codec 的变化。

最终点击路径 p50 74.11 ms，自动路径 p50 390.82 ms。自动筛选仍包含现有的 300 ms 防抖，因此**自动路径未达到 100 ms**；结果 JSON 的总体 `referenceTargetMet` 仍为 false，不能仅凭测试 PASSED 宣称全部性能目标通过。

## 改动

### 协议转换

`STC.SalesTrading.Plugin/Ficc/Protocol/ProtocolCodec.cs`：

- 用线程安全缓存保存类型的属性及 JSON 字段名，避免每条报价、每次递归重新读取反射特性。
- 初始化父模型基线时，已完成初始化的子模型尚未编辑，编码结果就是其原始 JSON；直接复制该原文，避免重新递归编码整个子树。
- 一次编码或 Attach 操作内复用 JsonSerializer；不同操作、不同线程仍使用独立实例。
- 保留原始字段、基线及显式 null 语义。本轮没有删除编辑跟踪，也没有新增只读协议模型体系。

### 管理页更新

`Modules/QuoteMgmt/ViewModel/MgmtTodayViewModel.cs`：

- 用索引替换已有展示记录，补入新增记录、移除多余尾部记录，替代每次先 `Rows.Clear()` 再逐条添加。
- 避免列表先清空导致 WPF 销毁后重建整批可见行；实际 Render 优先级操作之和 p95 从 145.41 ms 降为 20.63 ms。
- 替换完整展示对象，仍更新价格、基础数据等字段；不以 revision 相同为由跳过刷新。
- 原有筛选刷新清除选择的行为保持，避免操作到已被过滤掉的旧报价。

本轮修改范围为客户端。没有变更 Java 服务、网络协议、服务端筛选语义或自动筛选防抖间隔。

## 验证

1. Release 插件与 UI 测试程序构建通过。
2. 协议契约：历史协商场景捕获数据 **154 项通过**，完整增量业务捕获数据 **279 项通过**。其中新增检查覆盖嵌套修改、数字 token 保留、未知字段、显式 null、输入/输出 JSON 隔离及并行操作。
3. 两次 500 条桌面基准均核对全部返回 ID 和条数；40/60 条结果交替覆盖集合增长与缩短，实际生成 19–20 个行容器。两轮清理均成功，基准剩余报价清单为空。
4. 管理页功能用例 `07-management-filters` 通过：先选中报价，再筛选至空、恢复、搜索至空、重置；每次同时核对实际表格与 VM，并确认旧选择不会遗留。用例创建的报价已读取确认 DELETED。

性能终点仍为布局后的 WPF Rendering 回调及测试 continuation，不是显示器像素呈现。单样本首次筛选独立记录，未计入预热分位数。探针与 dispatcher 钩子保持启用用于同口径比较，未单独量化其开销。
