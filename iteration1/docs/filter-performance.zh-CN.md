# 前端筛选延迟测试

## 测量目标

目标为用户确认筛选条件后，首批报价结果在网格中完成重绘的样本 P95 ≤ 100ms。另行记录 `ficc.quote.view.open` 的请求/回复耗时，区分后台查询链路与前端更新成本。

**50,000 指服务端可搜索的报价总数，不是一次下载并绘制 50,000 行。** 本轮沿用原型的 `limit=200` 和虚拟网格，只加载当前结果的前 200 行，条件变化时仍调用原有 `view.close → view.open`。行情视图、持续报价更新、并发用户和历史数据库搜索不属于本轮测试。

100ms 可作为低延迟目标；是否达到取决于筛选实现、排序、数据复制、返回体积、消息库、日志与 UI 重绘。不能仅凭 50,000 这个数量保证达标。[NN/g 对响应时间的说明](https://www.nngroup.com/articles/response-times-3-important-limits/)将约 0.1 秒视为接近即时反馈的体验尺度，这不是数据库性能保证。

## 实现与边界

- [外部驱动与看门狗](../scripts/test-filter-performance.py)：一次只运行一个数据档位，创建独立 QuoteSvr、GW 和临时 PostgreSQL schema。
- [固定测试数据 SQL](../scripts/filter-performance-fixture.sql)：全部为 U-001 的有效报价，均匀分布在现有 4 个模拟债券中，方向、收益率、交割条件按固定规则生成。
- [C# 计时与校验](../client/src/QuoteFormFilterPerformance.cs)：调用原型自身的 `OpenView()`，检查总匹配数及前 200 个报价 ID 和顺序。
- 临时端口为 GW `18700`、QuoteSvr `18780`。隔离环境采用 STC 的静态服务寻址，关闭 ZooKeeper 注册，防止普通客户端发现测试服务；正常演示配置不修改。
- 直接向独立 schema 生成只读查询夹具，不通过报价录入接口产生大批历史、提醒或实时推送。正常报价库不写入测试报价。

固定场景：全部有效报价、AAA 评级、AA+ 评级、企业债 + 买方 + 收益率区间、无匹配结果。每个场景默认预热一次、测量六次，串行请求之间间隔 250ms。预热也保留记录，但不计入统计。

每个阶段都使用真实 DPS、GW、Java 内存搜索和 C# JSON 处理。全部发送/接收消息仍记录在 JSONL 文件中，日志成本计入测试。为防止大回复拖垮文本框，屏幕消息预览限制为每行 1,200 字符、最近 200 行；文件日志保留完整消息。

## 操作

先完成已有 Maven 构建，保留本机 STC 兼容库、有效许可证和 PostgreSQL 配置。构建本次客户端：

```powershell
dotnet build iteration1/client/QuotePrototype.csproj --no-restore -m:1 -p:OutputPath=bin/FilterPerformance/
```

使用新客户端的“操作结果 / 开发工具 → 自动测试 → 筛选性能测试(500条)”按钮，或在项目根目录执行：

```powershell
python iteration1/scripts/test-filter-performance.py --quotes 500
```

结果位于 `iteration1/runtime/filter-performance/<运行编号>/`：

- `summary.json`：完成状态、各场景统计、内存余量及 schema 清理结果。
- `latency.json`：每次原始计时，包括预热。
- `benchmark.json`：固定条件、预期匹配数和报价顺序。
- `quotesvr.log`、`gateway.log`、`client.err`：独立进程诊断日志。

默认仅测 500。支持手动指定 `2000`、`10000`、`50000`，脚本不会自动升级档位；每次先检查前一档的耗时、内存和 UI 响应情况。如果小规模已经暴露明显延迟，先定位问题。

```powershell
# 在检查较小档位后，单独选择下一档；不要把这些命令串成自动加压循环。
python iteration1/scripts/test-filter-performance.py --quotes 2000
# 50,000 档位的命令格式：
# python iteration1/scripts/test-filter-performance.py --quotes 50000
```

保持测试窗口可见，避免最小化或完全遮挡造成绘制等待。每轮完成后自动关闭测试进程并移除临时 schema，结果文件保留。

## 停止条件

外部 Python 看门狗每 100ms 检查进程与可用物理内存。限制如下：

| 条件 | 处理 |
|---|---|
| 可用物理内存少于 2GB | 停止当前轮 |
| 测试子进程合计提交内存超过 1GB | Windows Job Object 限制 |
| UI 心跳超过 2 秒不更新 | 终止测试进程 |
| 单次筛选超过 1,500ms | 保存已取得的样本，停止后续请求 |
| 网格重绘等待超过 1 秒 | 停止当前轮 |
| C# 测试进程超过 50 秒 | 外部终止 |
| 独立服务启动超过 25 秒、SQL 进程超过 15 秒 | 停止并清理 |

测试进程属于独立 Windows Job Object；看门狗意外退出时也会结束这些子进程。它只处理自己启动的进程。若因内存不足或数据库不可用导致临时 schema 无法删除，`summary.json` 会记录 `schemaRemoved=false`，恢复后按其中的准确 schema 名称清理。

该模式不加入常规自动测试或 Jenkins 默认构建。

## 指标口径

| 指标 | 包含的时间 |
|---|---|
| `closeMs` | 关闭旧视图的完整调用，包括 UI 调度 |
| `openRequestMs` | 工作线程调用 DPS 到解析回复、完成消息文件记录；包含 GW、后台、传输、序列化/反序列化和日志，不能当作纯后台搜索时间 |
| `openDispatchMs` | 打开视图时进入工作线程及返回 UI 线程的调度时间 |
| `applyMs` | 将回复放入客户端缓存并更新网格行数 |
| `paintAndDispatchMs` | 数据应用后，等待下一次网格绘制及 UI 后续任务恢复的时间 |
| `gridPaintMs` | 网格自身处理最近一次 `WM_PAINT` 的耗时；用于区分实际绘制和等待 UI 调度 |
| `totalMs` | 从开始改变视图到上述重绘完成，总体验延迟 |

重绘指标依据 WinForms `WM_PAINT` / UI 消息循环，不是物理显示器呈现时间，也不能直接断言其中全部时间都在绘制单元格。P50/P95 使用最近秩算法；只有六个测量样本时，P95 等于最大值，仅用于初步定位，不足以证明生产环境尾延迟。

## 首轮结果：500 条报价（2026-09-14）

完成 5 个场景，共 5 次预热和 30 次测量。结果和顺序校验全部通过；后台数据量为 500，前端实际加载 0、50、125 或 200 行。

| 场景 | 总延迟 P50 | 总延迟 P95 | 打开视图请求 P95 |
|---|---:|---:|---:|
| 全部有效报价 | 531ms | 576ms | 99ms |
| AAA 评级 | 512ms | 573ms | 89ms |
| AA+ 评级 | 504ms | 546ms | 57ms |
| 企业债 + 买方 + 收益率区间 | 487ms | 506ms | 35ms |
| 无匹配结果 | 67ms | 79ms | 19ms |

有结果的场景中，`paintAndDispatchMs` 中位数约 419–444ms，应用数据约 1ms。因此，当前记录首先显示回复之后的 UI 绘制/消息调度阶段存在显著延迟，需要进一步剖析，不能仅通过更换数据库解释。

本轮最低可用物理内存约 5.2GB，独立进程退出，临时 schema 已删除。**尚未执行 50,000 条档位，因此不能宣称 50,000 条时达到或达不到 100ms。** 本轮在 500 条停下，避免在已发现问题时继续加压。

原始记录：`runtime/filter-performance/20260914_134629_3498e196/`。首次驱动校验曾因 GW 日志级别导致就绪判定不匹配而超时退出，已修正判定；那次没有运行前端采样，临时数据也已清理。

源码还显示当前 `LocalSearchSvrClient` 对所有候选报价逐条补充属性、筛选与排序；`ViewService` 创建视图和计算总数会重复查询，并在截取 200 行之前复制匹配报价。后续应分别评估这些后台开销与已测得的 UI 等待，不在本次基准中预先优化后台。

## 首轮优化：保持 500 条（2026-09-14）

增加网格 `WM_PAINT` 计时后，确认未缓冲网格的实际绘制耗时约 340–445ms。`QuoteGrid` 启用双缓冲，将单元格先绘制到内存缓冲区，再显示到窗口。启用后的第一轮，非空结果的网格绘制中位数约 13ms。虚拟网格、列、字体、筛选接口和消息文件记录均保留。

另一个改动是 `MessageLog` 的脱敏处理：原先每层递归都会再次复制整棵子树，现在只复制一次，再遍历副本脱敏。不会修改业务回复对象，也不会减少日志中的报价内容。增加 `scripts/test-message-log.ps1` 验证嵌套对象、数组、空值、全部敏感字段、大小写匹配和原始对象不变。

最终版本仍测试 5 个场景，每个场景 1 次预热、6 次测量：

| 场景 | 优化前总延迟 P95 | 优化后总延迟 P50 | 优化后总延迟 P95 |
|---|---:|---:|---:|
| 全部有效报价 | 576ms | 90ms | 121ms |
| AAA 评级 | 573ms | 71ms | 95ms |
| AA+ 评级 | 546ms | 80ms | 87ms |
| 企业债 + 买方 + 收益率区间 | 506ms | 69ms | 98ms |
| 无匹配结果 | 79ms | 40ms | 55ms |

全部报价场景 P95 降低约 79%，但仍未达到 100ms；其他四个场景在本轮样本中低于 100ms。全部匹配数和前 200 条顺序校验通过。样本量小、同机进程调度会有波动，这些结果用于说明本次改动的效果，不能代表生产 SLO。

本次共执行一次短诊断和两次有明确代码变更的验证，均保持 500 条、单客户端串行请求，没有提高数据档位。最终运行最低可用内存 4426MB，所有临时 schema 已清理，测试进程已退出。50,000 条仍未执行。
