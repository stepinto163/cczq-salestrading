FICC 下午补充源码合并包 V1.0
日期：2026-11-02

一、变更原因与最终范围
1. 启动性能：QuoteSvr、NotificationSvr启动要装载Base资料和DM快照。原数值索引不断扩容复制、资料反复JSON转换、Base全量分页逐页遍历全表，加上串行初始化和过小初始堆，使启动耗时偏长。本次优化索引扩容、资料转换和固定快照分页，并行加载独立依赖，配套调整JVM；所有依赖成功后才继续就绪，失败保留异常，不改变筛选业务规则或公共接口。
2. 剩余期限：只有remainingYears数值不足以表达180D或3.30Y + 180D。本次复用原BaseSvr的TimeToMaturity，新增可选字符串remainingTerm；remainingYears保持原值。客户端缓存保存新字段，仅在“关注债券管理”的右侧候选列表演示，其余页面不改。
3. 范围：Common、QuoteSvr、NotificationSvr、BaseSvr、同事stc-client，以及单独列出的BondSearch Core性能补丁。Core生产改动仅RangeIndex扩容，保留同事接口、中文注释和业务语义；本次不能漏掉该依赖，否则启动优化不完整。

二、如何合并
1. 沿用上午“完整源码参考快照 + 组件增量patch + changes.json + manifest.json/SHA256”的形式。按差异合并，不要整目录覆盖QA仓库。
2. 增量基线：Common a276984；QuoteSvr 7a20767（须已合入上午原子提交及排序补充）；NotificationSvr及Core 5d009de；BaseSvr 9912168；同事客户端 a9313daca。目标提交以manifest.json为准：Common/Quote/Notification取下午1fab969快照，Core fb8976e，Base f17a006，客户端64fc3e14f。
3. 完整源码参考快照已含上午原子创建、价量可空和全部行情排序。尚未合入上午或排序补充的QA分支，应先合入此前包；不要强行套用不同基线的patch。
4. 同事客户端路径：colleague_20261029/stc-client；不是iteration1/stc-client/stc-client那份产品客户端。BaseSvr来自独立GitLab仓库feature/ficc-reference-data。本包无新的FiccBaseSvr进程。
5. build-support沿用上午父POM；qa-ui-tests沿用7a20767排序补充中的测试工具及72—77用例，本次未新增大规模桌面自动化。新增remainingTerm测试在sources/stc-client/tests和Base/Common源码测试中，现场单页验收见下文。

三、编译及部署核对
1. Java按已有QA流水线使用JDK8及原私服依赖，先构建安装Common，再构建安装Core，再构建QuoteSvr/NotificationSvr；BaseSvr按其原工程流水线构建。必须重新打包业务服务，确保包内Common/Core不是Maven缓存中的旧同版本JAR。
2. 客户端按现有STP构建方式重新编译，配套部署STC.Common.dll、STC.Data.Plugin.dll、STC.SalesTrading.Plugin.dll；不要只替换销售插件。FICC资料同步开关保持开启，服务仍指向BaseSvr。
3. 配置由Jenkins/Salt自动生成，共享配置仍在$ATS_ROOT/control，不增加手工example或另一套连接配置。核对源码config及Salt adapters中的base.snapshotPageSize=2000，核对最终服务包启动脚本。
4. 本次提交默认JVM：QuoteSvr -Xms1024m -Xmx3072m，NotificationSvr -Xms512m -Xmx2048m；两者均使用G1和-XX:MetaspaceSize=64m。64MB是触发阈值，不是元空间上限。QA若有环境覆盖，记录实际生效参数及主机内存，不盲目叠加旧参数。
5. 建议先升级并确认BaseSvr参考快照可用，再依次升级QuoteSvr、NotificationSvr，最后升级客户端。保留部署前整套包及配置便于成套回退，不混用不匹配的Common/Core。
6. 旧客户端缓存可继续读取；新客户端首次发现旧字段投影会补拉一次完整快照，失败仍保留旧缓存。补拉成功后恢复增量；不是每次启动都全量下载。

五、QA验收用例
用例01：启动性能与实际可用
- 同一QA机器、同一数据量、同样预热状态，保存升级前的启动时间、依赖行数、内存参数；升级后先单独测Quote，再测Notification，禁止同时起重复实例。
- 从发出启动命令计时，记录初始化各阶段日志；另记录Quote实际查询成功、Notification完成报价源同步且提醒接口查询成功的时间。只有日志INITIALIZED或端口监听，不能算最终可用。
- 预期：无初始化ERROR，Base/DM加载完整；查询能返回，数据量与升级前一致。比较同口径耗时并回报实际秒数，不以本机结果代替QA结果，不做大规模压测。

用例02：关注券候选列表期限（本轮重点）
- 使用已升级客户端登录QA，打开“关注债券管理”，选择或新建本次测试分组。
- 识别一只有效普通券、一只剩余不足一年券、一只未来有行权日的券。代码应从QA真实资料选择，不能假定示例日期永久有效。
- 对照同一轮BaseSvr ficc.reference.sync返回的Datas[].FiccReference.remainingTerm，候选列表逐字显示相同期限，例如3.30Y、180D、3.30Y + 180D；鼠标停留可看完整文本。源缺失时不伪造行权段。
- remainingYears仍是独立数值；其他报价/行情页面不因本演示切换显示。取消窗口并清理本次新建分组。
- 协议示例（示意值，不代表指定券当前真实期限）：
  {"securityId":"示例券.IB","remainingYears":"3.7956","remainingTerm":"3.30Y + 180D"}

用例03：旧缓存升级与再次启动
- 保留一份升级前客户端缓存，升级DLL后首次登录，确认日志projectionRefreshRequired=True触发完整补拉，成功后候选期限可见。
- 正常退出后再次登录，缓存日志应为False并恢复增量，不因字段升级重复全量下载。网络失败的保留旧缓存行为由组件回归覆盖；不要为验证它中断共享QA服务。
