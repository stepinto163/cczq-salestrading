二、本次三个业务改动
1. 报价失败提示补足上下文。
   原因：原提示不能说明具体哪条报价、哪只券或哪个输入值出错。
   处理：Common/QuoteSvr在中文提示及错误详情中补券码、报价ID、批量请求项、机构/交易员ID、字段实际值或版本信息；沿用原错误码和接口。
2. 拒绝QT上一日迟到的报价或更新。
   原因：日终已处理旧报价，但旧消息隔天到达仍可能新建今日草稿。
   处理：QuoteSvr按sourceTime原日期和quote.endOfDay.zone判断，在路由及写入前拒绝过往日期或非法时间。不是按tradeDate判断，不改变现有cutoff时间。QtIntake对明确的sourceTime校验拒绝存入rejected并释放队首，其他网络或权限错误仍保留原重试方式。
3. QT报价自动识别CRM机构及交易员。
   原因：只有QT名称没有CRM ID，尤其机构简称，原来不能直接完成确认。
   处理：机构全称/简称精确匹配优先，无精确候选时按“CRM名称包含输入名称”回退；去首尾空白并忽略大小写，不删除支行等信息。读取全部候选页后仅唯一命中填ID，多义/无匹配保留原文供人工选择。联系人只在已确定机构内按同样规则识别；已有ID不覆盖。匹配后由既有校验使用CRM规范名称。
   没有增加QT联系人下载或U48接口依赖。QT联系人API仅做过调查和只读实测，不属于本包功能。

三、合并及构建
1. 在已合并20261117-R1的分支上，进入各组件根目录检查对应补丁：
   git apply --check <解压目录>/patches/<组件名>.patch
   检查通过再git apply同一补丁。若QA此后有改动导致冲突，逐文件合并，不覆盖QA改动。
2. sources/下为各组件目标完整源码，可用于核对；配置文件是原受控内容，并非要求覆盖QA生成的环境配置。此次没有配置变更或数据库迁移。
3. 先构建安装cgws-ficc-saletrading-common 0.1.1-SNAPSHOT，再构建QuoteSvr和QtIntakeSvr。沿用既有父POM、依赖及Jenkins/Salt流水线，确保部署物包含新Common。
4. NotificationSvr没有源码改动，不提供重复源码；它也是Common消费者，若随本轮统一升级Common，请用QA既有NotificationSvr源码重新构建，使各服务依赖版本一致。不要把Common源码包当成独立服务部署。
5. BaseSvr、BondSearch Core、DM估值接入、客户端均无本轮源码变更。本包不重发上次的客户端历史页面补丁，前端代码由同事分支自行维护。
6. 升级时先暂停QtIntake转发，再升级Common及QuoteSvr，最后恢复配套QtIntake。保留既有收件箱，不能让同一QT FIX身份同时在本机和QA登录。
7. 源码与Salt配置不需新增参数或手工补文件。日志合并/拆分仅附说明，本次没有实际切换日志输出模式。

四、测试与QA回归
1. 报价错误：缺券、机构/联系人无效、字段类型/值无效、版本冲突、批量第二项失败；错误要能对应具体券和报价，失败不得修改原报价。
2. QT时间：昨日来源今日到达应拒绝；今日来源且交易日为明日应正常创建；昨日同协商更新不能覆盖今日草稿；拒绝后后续有效消息继续处理，拒绝档案可查。
3. CRM识别：机构全称精确、简称精确、唯一包含、无匹配、多义；联系人同名但不同机构、同机构多人、空联系人、已有手选ID；分页后才出现精确候选或重复名称的情况。多义不许自动选第一条，CRM异常不能当无匹配。
4. 日志检查QT_CRM_MATCH的mode/state/matchedId；匹配范围按最终归属人及现有CRM访问规则，不新增权限策略。
5. 在QA现有客户端做端到端：QT入站→QuoteSvr→CRM查询→报价确认显示→确认成功或中文选择提示。核对服务响应、数据库ID及界面，不能手工补上游应提供的字段后再声称通过。
6. 后端单元/集成测试位于各模块src/test；QtIntake包含LateQuoteLiveCheck、QtCrmLiveCheck本机FIX回放程序。手动回放程序的本机CRM样本、账号、路径属于本机验收前提，QA必须换成本环境已存在记录；不要直接复制本机ID当QA数据，不连接外部QT造消息。
