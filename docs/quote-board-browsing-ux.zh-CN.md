# 实时报价列表的浏览体验（产品讨论稿）

日期：2026-09-17。

## Web实时模式与浏览模式

Web滚动后进入浏览模式：保留当前行的位置，不自动插入或重排；已有记录可更新数值，失效记录保留占位并禁止报价操作。滚动跨批次仍调用原有分页查询接口，替换当前批次。

按钮改为“浏览中 · 返回实时”；收到变更后显示“有 XX 条变更”。按当前视图内发生变更的不同记录计数，同一记录多次变化只计一次（行情按债券价格簿计数）。点击后使用原筛选条件重新查询第一批、回到顶部、清空计数并恢复实时更新。新筛选同样恢复实时模式。客户端暂时共用同一个业务视图的面板也共用此状态。

下文中Web“返回最新”入口以此交互替代，C#本轮不变。

本文面向产品和交互设计。本轮服务、C#及Web客户端已实现分页查询和实时更新规则。Web在滚动到当前批次底部或顶部时自动查询下一批或上一批，只保留“返回最新”按钮，并显示加载中和末尾提示；C#保留上一批／下一批／返回最新入口。客户端目前只缓存当前一批，滚动跨批次时替换当前列表，不累计追加全部记录。技术说明见[前后端协作说明](quote-board-paging-collaboration.zh-CN.md)。

同一浏览规则适用于报价列表、行情列表和提醒列表。下文以报价为例：行情每行是一只债券的价格簿，提醒每行是一条通知；它们分别加载和更新，不混成同一种数据。行情中一只债券内部的价格档次顺序仍由服务器计算。

最新决定：服务器告诉客户端“报价变成什么样、是否符合筛选条件”，**不指定报价显示在第几行**；客户端按更新时间自行排列顶部这一批数据。用户看到的交互规则如下。

## 核心原则

**看最新报价时保持实时，往下阅读时尽量保持稳定。** 用户通过滚动浏览，不必看到页码；系统在后台分批加载数据。

以下每组三条仅用于举例，不代表实际产品每次只能展示三条。

## 1．顶部显示最新报价

假设当前最前面三条是 A、B、C。新的报价 J 到来，且符合当前筛选条件：

```text
原来：A B C
更新：J A B
```

C 仍然存在，只是不再属于最前面的三条。已有报价被修改后，如果更新时间变成最新，也可能移动到顶部。

因此，顶部是持续变化的“最新报价区”，按报价更新时间从新到旧排列。

例如C修改后成为最新报价，客户端自行把[A,B,C]排成[C,A,B]。只需整理当前少量记录，不需要把所有报价下载到客户端。

## 2．报价不再符合条件时，从列表中消失

例如用户选择“只看急报价”，C 被取消“急”标记：

```text
原来：A B C
移除：A B
补位：A B D
```

客户端移除C后，自动向服务器重新请求顶部这一批数据，得到[A,B,D]，用户不必手动刷新。如果没有更多匹配报价，则保留实际条数。短时间内多次移除可以合并为一次请求。

如果消失的是A，B和C自然向前移动，不需要服务器逐条通知它们的新位置。

**从当前列表消失不代表报价被删除**，也可能只是状态或属性不再符合筛选条件。反过来，一条原本不符合条件的报价，修改后符合条件，也可以进入最新报价区。

## 3．往下阅读时，尽量保持位置稳定

用户向下滚动，正在阅读后续批次的 D、E、F 时：

- 新报价 J 到来，不插入这段正在阅读的内容。
- D 的价格等字段发生变化，可以更新显示，但不因更新时间变化而重新排列。
- E 被删除或不再符合条件，就移除 E；这段内容暂时可以少一条，不自动补位。
- 切换到其他批次或主动刷新时，重新取得当前结果。

建议提供“返回最新”入口，让用户主动回到顶部，恢复最新报价的实时排列。

稳定阅读指尽量避免新增报价和重新排序打断阅读，不代表冻结报价内容。

## 4．改变筛选条件，开始一次新的浏览

例如从“全部债券”切换为“银行发行”，列表重新加载，从最新的匹配报价开始展示。

报价操作始终针对用户选中的那条报价，不能因为列表位置变化而误操作其他报价。

## 需要产品接受的取舍

这次简化主要改变前后端分工，用户体验目标保持不变：服务器不持续指挥每一行的位置，客户端只排列少量数据；往下阅读时继续保持位置稳定。移除后的补位需要一次查询，期间可能短暂少一条。

本方案优先照顾实时查看和稳定阅读，**不保证用户向下滚动时，恰好把所有报价不重不漏地看一遍**。报价持续变化，跨批次加载时可能再次看到某条报价，也可能跳过某条报价。因此，这种浏览方式不能用于保证完整性的导出。

历史查询没有实时订阅，不采用上述实时插入、移除和补位规则。

本轮讨论已接受的方向是：**顶部内容实时移动，后续正在阅读的内容尽量保持位置稳定。** “返回最新”的入口位置、更新提示和视觉效果由交互设计进一步确定。
