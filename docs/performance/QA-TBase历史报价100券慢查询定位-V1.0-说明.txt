TBase历史报价100券慢查询定位测试 V1.0
日期：2026-11-03

一、目的
上一轮QA的100券查询耗时10.12秒，其中10.116秒在history_daily_formal_order_idx扫描。
本次只定位这一项：比较索引选择和查询写法。不改产品源码、不部署、不修改业务表或业务索引。

二、三组对照
A 原查询：保持当前5个索引、ANY券数组、正式报价及权限条件、精确总数、排序和50行分页JSON。
C 逐券定位：保持5个索引及所有业务条件；用唯一券ID数组展开后逐券LATERAL查询，OFFSET 0保留子查询边界。
B 无排序索引原查询：只删除本次临时表的两个排序优先索引，SQL与A完全一致，保留券代码优先索引。
B不保证强制选某条索引，须看实际计划；C仅是100券诊断，不是已决定的生产方案。

执行顺序为A1、C1、A2、C2、A计划、C计划，再移除测试表排序索引，执行B1、B2、B计划。
每种两次计时和一份EXPLAIN ANALYZE BUFFERS JSON，全部串行。不要同时启动多个脚本。

三、数据与一致性
重新生成与前一轮相同的100万不同报价、10万券、28个日期，仅筛选前100只券。
上轮测试表已ROLLBACK，因此需要重新造数；本次不是把业务数据搬到测试表。
预期匹配1000条，返回50条；所有成功查询的完整JSON逐一与首个成功结果比较，包括总数、字段、顺序。
最终应有successful_queries=6、successful_variants=3、distinct_result_fingerprints=1、completed_plans=3。
若A超时、B/C成功，仍有定位价值，但不能说三种结果都已验证一致。TIMEOUT/ERROR必须如实回传。
保留正式报价和权限过滤，不以删除状态条件制造更快的结果。

四、执行
在获准的QA测试数据库、同一个连接执行整个SQL，保存全部输出。
需要CREATE SCHEMA权限，建议至少3GB测试空间；已有同名schema时直接失败，不覆盖或删除已有数据。
推荐在QA Linux通过psql执行，外部8分钟上限：
timeout --signal=TERM --kill-after=5s 480s psql -X -v ON_ERROR_STOP=1 -h 数据库地址 -p 端口 -U 用户 -d 测试数据库 -f "QA-TBase历史报价100券慢查询定位-V1.0.sql" > tbase-history-100-diagnostic.txt 2>&1
连接参数沿用QA既有值；密码使用既有认证方式或交互输入，不放在SQL/邮件/输出文件中。
如无timeout命令，使用等效外部进程看门狗；不要省略整轮超时保护。
数据库工具运行需同一连接、整份执行，并由操作者在8分钟上限取消及关闭连接。

准备语句上限180秒，锁等待3秒，诊断查询20秒；20秒用于容纳已观察到的10秒基线，不是生产超时调整。
不修改work_mem、planner开关或全局配置，不访问DM，不执行VACUUM。
脚本只在新建的ficc_history_100_probe内操作，所有建表/造数/删测试索引均在一个未提交事务中。
结束ROLLBACK，remaining_schema必须为null。出错或取消后同连接ROLLBACK或关闭连接，严禁COMMIT。
外部超时后如进程仍未退出，需按该测试连接核实回滚，不要误停业务连接。

五、请回传
完整tbase-history-100-diagnostic.txt，包括版本、统计信息、索引定义、六轮结果、三个执行计划及清理结果。
同时注明CPU/内存、数据库部署方式、测试时其他负载；外部超时或中途退出也请说明。
重点比较每个计划的索引名、Index Cond、Actual Rows/Loops/Time、Shared Hit/Read Blocks及估计行数。
Shared Hit是访问次数，不是不同物理块数；不能仅凭此认定发生了百万次JSON提取。
B/C明显更快只是定位证据，尚需1万/10万券和深分页验证后才能决定产品改法。

六、本机已验证与限制
本机PostgreSQL16仅用1000条数据、100个筛选券进行功能检查，非百万性能测试。
普通样本和混合状态样本各6次查询、3份计划完成；三方案完整JSON一致，独立复查schema已清理。
混合样本包含待确认、未确认即删除及已确认删除，验证前两者排除、后者保留。
每次本机验证使用40秒外部进程看门狗。未连接QA，TBase执行和百万规模性能待本次回传。
该诊断不包含迁移、触发器、真实DM匹配、并发、JDBC/网关/客户端，也不输出两次样本的P95。
