# 报价状态字段及组合说明

- 版本：V1.0
- 日期：2026-11-18
- 范围：说明当前后端实现中报价状态字段的含义及展示规则，供前端和QA参考。本文件不引入新的状态或业务规则。

## 1. 字段含义

| 字段 | 中文含义 | 当前取值及用途 |
|---|---|---|
| `status` | 报价业务状态 | `PENDING_CONFIRM`（待确认）、`ACTIVE`（有效）、`REFERRED`（已撤销／已失效）、`DELETED`（已删除）。用于业务状态判断。 |
| `statusReason` | 状态补充原因码 | 当前代码仅设置 `PENDING_EXPIRED`，表示报价尚未确认便在日终过期；其他场景未设置。 |
| `statusText` | 状态中文展示文案 | 当前代码仅设置“待确认过期”。非空时优先展示；为空时按 `status` 映射中文名称。不能用该文案代替业务状态判断。 |

下表中的“空”表示未设置；接口JSON可能省略该字段。表中记录的是当前代码生成的组合，不代表数据库已有历史数据必然全部符合这些组合。

## 2. 状态组合与业务场景

| 业务场景 | `status` | `statusReason` | `statusText` | 中文说明 |
|---|---|---|---|---|
| 新建后尚未确认 | `PENDING_CONFIRM` | 空 | 空 | 待确认，尚未成为有效报价，不参与有效行情价格计算。 |
| 确认成功／创建时直接确认 | `ACTIVE` | 空 | 空 | 有效报价，参与行情展示及价格计算。 |
| 用户主动撤销 | `REFERRED` | 空 | 空 | 已撤销，不再参与有效行情，保留历史。 |
| 被相同业务条件的新报价替换 | `REFERRED` | 空 | 空 | 原报价自动撤销，保留历史。 |
| 有效报价日终撤销 | `REFERRED` | 空 | 空 | 系统按日终规则撤销报价，保留历史。 |
| 待确认报价日终过期 | `REFERRED` | `PENDING_EXPIRED` | 待确认过期 | 未经确认便过期，从待确认列表移除，仍可查询历史。 |
| 删除普通待确认草稿 | `DELETED` | 空 | 空 | 逻辑删除；从未确认且主动删除的草稿不展示在业务历史中。 |
| 删除曾确认的已撤销报价 | `DELETED` | 空 | 空 | 逻辑删除，仍保留业务历史。 |
| 删除已经过期的待确认报价 | `DELETED` | `PENDING_EXPIRED` | 空 | 保留原过期原因，清空中文文案，展示为已删除；因从未确认，删除后不展示在业务历史中。 |
| 对已撤销报价执行 `unrefer` | 新记录为 `ACTIVE` | 新记录为空 | 新记录为空 | 复制业务字段生成新的有效报价；原报价的三个状态字段保持不变。新记录须通过原有校验。 |

## 3. 关键规则

1. “待确认过期”不是第五种 `status`，而是 `REFERRED` 加 `PENDING_EXPIRED` 的组合。`REFERRED` 不代表该报价一定曾经确认。
2. 主动撤销、新报价替换、有效报价日终撤销的三个字段完全相同，不能仅凭这些字段区分原因；需查看历史操作记录中的操作人和原因等信息。
3. `DELETED` 表示逻辑删除，不表示数据库记录被物理删除。判断删除记录是否属于正式业务历史，还需检查 `confirmTime` 是否非空。
4. 删除操作会清空 `statusText`，但保留 `statusReason`。因此 `DELETED / PENDING_EXPIRED / 空` 是正常组合。
5. `unrefer` 不把原记录改回有效状态，而是创建新报价，使用新的 `quoteId`，通过 `clonedFromQuoteId` 关联原报价。

## 4. 允许的状态操作

| 当前状态 | 当前允许的操作 |
|---|---|
| `PENDING_CONFIRM` | 修改、确认、删除；符合日终条件时系统转为 `REFERRED / PENDING_EXPIRED / 待确认过期`。 |
| `ACTIVE` | 修改、撤销；符合条件时由系统日终撤销或被新报价替换。有效报价不能直接删除，须先撤销。 |
| `REFERRED` | 删除，或执行 `unrefer` 创建新的有效报价。 |
| `DELETED` | 不允许通过上述操作恢复或修改。 |

以上为状态层面的允许范围，实际操作仍须满足权限、版本和报价字段等其他校验。
