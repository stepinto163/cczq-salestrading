# 报价列表滚动与分页：前后端协作讨论稿

日期：2026-09-17。

适用范围：报价、行情、提醒三类列表共用本稿的分页、客户端排序及补位规则，各自使用独立模型和频道。以下以报价举例。

本轮已在服务、C#客户端和Web客户端实现：**后端推送数据及筛选匹配变化，不发送行位置；前端自行维护第一页的顺序。** 三类view.extend已替换为view.query，协议见[API规范](ficc-api-spec.zh-CN.md)。旧客户端与服务需同步升级。

## 1．基本方案

用户通过滚动浏览，客户端在后台按页请求数据，不必显示页码。一个筛选条件有50,000条结果，不代表客户端需要加载或渲染50,000行。

- 后端负责过滤、查询时的全局排序、按页返回数据及相关数据变化推送；不持续计算每个客户端的行位置或替换行。
- 当前前端只保存一页，负责第一页的插入、排序、裁剪和补位请求；相邻页缓存暂未加入。C#保持虚拟网格，Web只渲染本页数据。
- 第一页跟随最新变化；第二页及以后保持阅读稳定。
- 本轮不引入quote-ID滚动锚点，也不要求后端持续维护每一页的精确全局排名。

排序沿用业务规则，报价列表为`updateTime DESC, quoteId ASC`，同时间以quoteId稳定排序。前后端必须使用相同规则；前端只整理少量已加载行，不对50,000条全量数据排序。

## 2．查询与订阅

沿用DPS请求/应答和订阅/发布：viewId标识面板，streamId标识推送流，pushTopic为实际订阅地址。报价、行情、提醒仍使用各自的模型和频道，不合并。

```text
客户端                                    后端
  ── 创建流并订阅pushTopic ────────────────→
  ── 查询view1第1页，pageSize=3 ───────────→
  ←─ 当前页[A,B,C]、totalCount、sequence=S ─
  ←─ 后续相关数据变化，sequence>S ──────────
  ── 滚动到下一页，查询第2页 ──────────────→
  ←─ 当前页[D,E,F]、totalCount、sequence=S2 ─
```

分页含义为`offset=(pageNumber-1)*pageSize`，每次只返回所请求的一页，不返回从第1行开始的累计结果。pageNumber从1开始。已注册`ficc.quote.view.query`、`ficc.price.view.query`、`ficc.notification.view.query`，各自复用原view条件及订阅，替代旧extend。

查询期间先缓冲推送；安装查询结果后，只接续其sequence之后的变化。旧查询应答不能覆盖较新的翻页／筛选请求。缺号或流重建时重新查询，不能假定DPS会自动补齐所有业务消息。

推送继续区分三类信息：

- `quotes`：本批报价的完整显示数据，同一报价被多个view引用时只发送一份。
- `reports`：报价操作结果及操作人、时间、requestId等信息，不负责列表排列。
- `views`：用`upsertIds`指明各view应插入或更新的记录，用`removeIds`指明退出筛选范围的记录，并给出totalCount。**不包含`place/index`。** 对应接口见API规范H16/H17、H26/H27、H51/H52及S01/S02/S08。

前端不能仅凭`quotes`判断报价属于哪个面板，因为该集合还可能包含其他view或操作报告所需的数据。`views`负责说明匹配关系；“仍匹配但被第一页裁剪掉”由前端决定，不当作退出筛选范围。

## 3．第一页：新增、更新与移除

假设pageSize=3，后端完整排序结果为：

```text
A B C | D E F | G H I
```

| 事件 | 后端职责 | 前端处理 |
| --- | --- | --- |
| 新报价J匹配条件 | 推送J的完整显示数据及所属view，不计算行位置 | 插入后按统一规则排序，保留前3条；若J最新，则从[A,B,C]变成[J,A,B] |
| C被删除或退出匹配范围 | 推送C的移除信息，即使C的新状态已不符合过滤条件 | 先移除C，再合并触发一次第一页查询，由后端返回[A,B,D] |
| A/B/C字段更新且仍匹配 | 推送新版本及所属view，不计算行位置 | 按ID替换、重新排序，不重复追加同一条记录 |
| 已有但未加载的J更新后匹配 | 推送J的新版本；不能仅推前端已经有的ID | 与新增一样，插入、排序，保留前3条；是否进入第一页由前端比较决定 |

例如C修改后成为最新报价，前端自行把[A,B,C]排成[C,A,B]。如果A退出条件，前端删除A，B和C自然前移；后端无需再通知B、C的新位置。

补位规则：**第一页因实时事件移除了一条已加载记录，才触发补位查询**。包括删除、Refer后不再属于有效报价列表，以及更新后不满足过滤条件。是否移除取决于该view的条件，例如包含REFERRED的报价管理列表不会因为Refer就自动移除。

短时间多次移除合并为一次查询；查询期间又发生移除，记录刷新需求并在应答接续后检查。查询本身返回不足pageSize条时直接接受，可能全部结果本来就不足一页，不能因此循环重查。

这一简化依赖普通报价修改更新updateTime，不把更新时间回写为更早值。若发生时间纠正导致已加载报价排序下降，或基础资料批量变化影响筛选，则重新查询；不能仅靠少量本地记录找出未知的补位候选。无需为这些情况持续维护全局行位置。

## 4．第二页及以后：稳定阅读

本稿约定后续页展示“最近一次查询得到的那组记录”，期间：

- 已加载记录字段更新可以显示，但不因排序变化搬动位置。
- 新增报价不插入正在阅读的后续页。
- 删除或退出条件的记录移除，不自动从其他页补位。
- 切换页、手动刷新或改变筛选条件时，重新查询后端的当前结果。
- “返回最新”重新查询第一页，恢复第一页的实时维护规则。

因此后续页可能暂时不足pageSize条，也不保证一直对应全局排序中的同一排名范围。数据变化期间切换页可能遇到重复或跳过的记录；这是本方案为简化实时分页而接受的限制，不适合作为完整导出遍历。缓存相邻页也不能消除该限制。

## 5．实现边界

- 第一页订阅必须覆盖“新匹配记录”和“原来匹配、现在退出的记录”，不能只检查变化后的数据；后续页需继续跟踪已返回记录的更新及移除。
- 后端仍需维护筛选订阅并判断匹配变化；取消行位置维护不等于取消订阅。第一页可能接收最终被前端裁剪掉的匹配更新，这是减少后端排名计算的取舍。
- 先完成订阅登记和查询边界，再发布后续事件，避免初始数据与增量之间出现空档。分页切换时避免在途旧页消息污染新页。
- 查询回复返回totalCount；移除或新增在全结果中的计数由后端确定，前端不能仅按本地行数推算。
- 对报价执行修改、Refer等操作始终使用quoteId及该报价的revision，不使用行号、pageNumber或价格簿版本。
- QuoteView每行是报价，标识为quoteId；PriceView每行是债券价格簿，标识为securityId，使用`ficc.price.report.<sessionId>`。新增一条报价可能只更新已有债券的价格簿，不一定新增一行行情。
- NotificationView每行以notificationId标识，使用notifications数组及独立notification.report频道。三类views都用upsertIds／removeIds；行排序均为updateTime降序、各自ID升序。Price的updateTime由后端在完整匹配报价中计算并返回，不从BEST/DEPTH截断后的条目推导；删除最新报价导致该时间下降时，第一页重新查询。券内价格档排序仍由后端完成。
- 历史查询没有实时订阅，按日期范围查询并分批读取。

相较旧实现，取消持续计算`place/index`及自动替换行，改为前端排序、必要时查询补位；按页查询避免反复返回累计前缀。QuoteSvr 的普通报价事件已改为下面的增量计算；初始查询、失效重算和 NotificationSvr 仍保留各自的完整计算路径。不保证推送流量一定更小，也不代表50,000条数据的性能已经达标。

## 6．QuoteSvr 增量维护（2026-09-29）

协议字段和客户端处理方式不变。本次改变的是服务端计算方式，范围为 QuoteSvr 的报价和行情 view。

- 创建 view／查询页：计算匹配结果。报价保存 ID＋revision，仅捕获请求页的记录版本和序号，在锁外转换该页 JSON；行情仍保存内容指纹。`totalCount` 直接来自已计算的匹配集合，不重复查询一次。
- 普通报价变更：用与查询共用的归属、状态及条件判定检查该报价。新匹配则 upsert，退出则 remove，仍匹配但内容变化则 upsert，不匹配且原先不在集合则不推送。未变化报价不重新序列化／哈希，不重新扫描全体报价。
- 行情变更：启动时从恢复的报价建立债券→报价索引，每次已提交的报价变更更新索引。只重建受影响债券的价格簿；报价换券时同时处理旧券和新券。最佳档退出时以该券剩余报价补档；最后一条匹配有效报价退出时移除该券。不同 view 的过滤、深度和权限继续分别计算。
- 相关筛选组／关注组修改：只重算引用该组的 view。删除被引用的组仍发送 `RESET_REQUIRED`，客户端关闭并重建失效 view；其他 view 不因此全量重算。
- 观察到基础资料版本变化或计算失败后恢复：重建匹配指纹，避免只处理某一报价而漏掉其它成员变化。版本由基础资料适配器提供；当前 STC 适配器按需读取映射资料，**这不是全体基础资料变更的实时通知保证**。资料源变化的主动通知／定向失效仍需后续接入，手动重查会重新读取所需资料。
- 请求、变更、关闭 view 仍受同一个服务锁保护。先完成的更新可以先发消息；关闭完成后新事件不会再为该 view 计算增量。网络中已经发出的旧消息仍需客户端按 viewId／streamId／sequence 丢弃。

当前仍有明确成本：每个报价事件遍历活动 view；同券价格簿重建需要处理该券报价并排序；各 view 保存全部匹配版本／指纹；首次查询／分页仍计算完整匹配结果。报价页应答转换可由请求线程在锁外并行完成，但过滤和状态修改仍在锁内，没有引入并行匹配、共享条件缓存或队列限流。不能把单条增量优化解释为高并发容量承诺。5000／10／4 的端到端验收目标、已测结果和未完成项见[性能基准](quote-performance-benchmark.zh-CN.md)。

功能验证使用 Java 8：`IncrementalViewPageTest` 的 3 个缓存单元测试通过；`IncrementalViewSmoke` 在隔离 PostgreSQL schema 用 4 条固定报价完成 344 项断言，包含不同用户／过滤条件、进入／退出／原地更新、价格最佳档补位、换券、删组、分页后续增量、基础资料版本失效，以及两个调用者的更新／关闭次序检查；增量结果逐次与完整查询结果核对，并检查普通事件没有读取无关债券。原 `BusinessSmoke` 的 50 项生命周期断言通过。上述断言数不是独立业务场景数；没有进行 DPS/GW、UI、压力或延迟验收。
