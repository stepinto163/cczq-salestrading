# 20261120-R2：交易日、结算日与旧清算编码

## 本轮最终要求

修复节假日后的交易日；新增实际结算日 `settlementDate`；恢复 QA 识别接口旧编码。仅修改 ParserSvr、Common、QuoteSvr，不改客户端、BaseSvr、STC共享库和数据库。

R2 替代未发送的 R1 包。R1 的“明+0/+1 返回日期字符串”方案已被用户否决，不再作为最终行为；没有采用 settlementDays 或新枚举方案。

## 前端对接示例

接口 `ficc.quote.accurate.identify`，行位于 `Data.Datas`。2026-11-20（周五）真实接口实测：

| 输入 | tradeDate（交易日） | settlementDate（实际结算日） | settlType |
|---|---|---|---|
| T+0 | 2026-11-20 | 2026-11-20 | "1" |
| T+1 | 2026-11-20 | 2026-11-23 | "2" |
| 明+0 | 2026-11-23 | 2026-11-23 | "3" |
| 明+1 | 2026-11-23 | 2026-11-24 | "4" |

```json
{"tradeDate":"2026-11-23","settlementDate":"2026-11-24","settlType":"4"}
```

- `tradeDate`、`settlementDate` 均为 `yyyy-MM-dd` 字符串。前者是交易日，后者是结算日，不能互相替代。
- 识别接口的 "3"/"4" 仍是明日 +0/+1，不能按正式报价接口的 T+2/T+3 解释。
- **前端必须读取服务端 tradeDate，停止按 3/4 自行 DateTime.Now.AddDays(1)。** 仅恢复编码并不能修复旧客户端的日期显示。
- 本机同事客户端9e9e41ac4：`Gateway/Contracts/Parser/IdentifyQuote.cs` 增加 TradeDate、SettlementDate 属性；`Gateway/GatewayQuoteService.cs` 的 MapIdentifyQuote 优先使用返回的交易日。新接口已返回日期时不可忽略后再按本机日历猜日期。本包不含客户端源码，由同事实施。
- +2及以上维持上一轮已有的 `MM.dd+N` 表达，不新增枚举，也不降成 +1。例如明+3返回 `11.23+3`、交易日2026-11-23、结算日2026-11-26。旧前端对 +N 的映射仍不完整，此项兼容性未解决；本轮未实现“所有场景统一数字编码”。
- 新字段覆盖 Parser 原始、普通识别和 Quote 新增报价识别；撤价建议沿用已有报价数据，尚无持久化的 settlementDate 时可能不返回此字段，不凭当前日期重算旧报价。

## 日期计算与部署

ParserSvr复用基础包 `WeekDateSettlement.getDateBySettlementType` 以及 BaseSvr 下发的 CNY_CIB 日历：明日取下一交易日；结算日沿用基础包“交易日加 N 个自然日，遇休市顺延”规则。本轮没有替换为“累加 N 个交易日”算法。日历未加载/未覆盖时失败，不生成假日期。

Parser 原始响应 tradeDay 为交易日、settlementDay 为 +N，新增 settlementDate；普通响应增加同名日期字段。QuoteSvr保留日期原值并恢复1/2/3/4识别编码。

1. 按 manifest 各模块基线合并补丁，完整源码供核对。Common 基线为已发送20261119-R3；Quote为20261119-R4；Parser为20261119-R3。
2. 先编译安装Common，再构建QuoteSvr；ParserSvr正常构建。部署Common到QuoteSvr运行依赖，协调升级ParserSvr和QuoteSvr。
3. 无数据库迁移，无新增配置，不需要手工复制example文件；QtIntake不需更新。
4. 前端同事完成日期映射后，QA验证页面显示和确认提交的tradeDate、清算速度；没有通过该验证前不得标记整体验收通过。
