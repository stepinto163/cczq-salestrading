# 归属交易员姓名下发：背景、审查结论与延期方案

日期：2026-11-28

**状态：已完成方案讨论，低优先级，延期实施。QA补丁未合并，未部署。恢复时先读本文，不直接应用旧补丁。**

## 一、要解决什么问题

FICC页面的“长城交易员”是报价本方归属人的姓名，对应`ownerUserId`；不是对手机构联系人`contactName`/`TraderName`，也不一定是当前登录人、创建人或最后操作人。QT群路由可能把报价分配给另一名本方交易员，因此必须以最终归属人为准。

当前客户端根据服务端返回的归属人ID，从宿主AdminSvr用户缓存解析姓名。缓存未覆盖某个用户或未刷新时，可能显示“未知用户”，行情部分旧路径还会回落显示ID。不同页面的现有兜底并不统一。

QA因此提出在服务端报价payload中增加`ownerUserName`，复用V1.8.9引入的`StcOwnerSearchDirectory`。该目录读取`stc_tbook_users(userid, username, name)`，姓名优先、登录名兜底，包括停用账号，以支持历史查询。名字用于展示，权限、归属、去重继续使用ID。

## 二、与biztypeid问题的关系

用户提供的`biztypeid-root-cause-report.md`是本次背景材料。`biztypeid`在相关STC链路中表示账号部门，影响用户目录筛选。已核实本机源码存在同步端不写部门、管理端可能空值覆盖、空部门查询落入全体启用用户、客户端缓存缺少及时更新等问题；QA人数及现场数据仅来自该报告，未在本轮重新查库。

姓名下发直接按userid查目录，**不依赖部门匹配，但也不修复部门分配、用户目录权限或客户端缓存失效问题**。不能把姓名下发完成称为这些问题全部解决。

报告中需保留的更正：用户同步先按userId再按username查找，所以变更上游ID不一定重建账号；用户目录返回全部人员不等于所有报价、成交权限都失效。

## 四、补丁审查结论

方向合理：按真实owner解析姓名、禁止客户端伪造该字段、不改变权限与去重键、仅扩展JSON payload而不增加数据库列。两个补丁在上述后端基线上`git apply --check`均通过；仅检查，没有应用。

尚不足以作为完整功能合并：

1. **提醒漏字段**：`NotificationService.notificationTrigger()`按白名单构建快照，未包含`ownerUserName`。
2. **行情漏字段**：`MarketEntry`及`PriceBookService.entry()`只投影`UserID`，未包含本方姓名。
3. **前端未接字段**：当前QuoteRecord DTO没有该属性，`GatewayModelMapper`仍从本地用户缓存映射。不是只改一行即可，需同事补DTO、相关页面映射及推送处理。
4. **只在创建时赋值**：旧报价和首次取名失败的报价不会在目录恢复后自动补齐；Unrefer继承原非空名字。需先确定姓名的时间语义。
5. **写入链路存在等待风险**：`displayName()`调用同步`get()`，60秒缓存到期会在报价事务中刷新目录。SQL超时3秒不包含全部连接等待；刷新失败后未更新成功时间、无失败退避，后续报价会再次查询。异常被捕获并返回null不代表不影响响应时间。
6. **验证不完整**：QA报告94项测试中28项跳过，新增3项常驻测试通过，1项PG门控测试未跑。PG例即使运行也使用lambda提供姓名并直接调用服务，不是实际目录、网关、客户端的端到端验证。本轮没有独立编译或运行补丁。

## 六、用户已认可的实施原则

1. **关键路径只读内存目录**：报价创建和响应生成不等待姓名数据库查询；刷新与业务调用分开，暂时刷新失败保留最近成功的显示名缓存。刷新调度、初次加载及失败退避细节在实施时确认，不擅自改变既有搜索失败契约。
2. **仅必要消息下发姓名**：实际展示姓名的报价行、价格簿条目、提醒快照应覆盖；不机械扩展所有消息。价格簿不能以“不需要姓名”为理由遗漏。
3. **保留分页及增量推送**：不为姓名额外下发整批报价、扩大页大小或增加价格档位；删除消息无需重复姓名。
4. **先保持协议简单**：现阶段不增加批次用户字典协议。若后续实测确有明显重复负担，再评估`ownerUserId→name`字典，不提前增加前端复杂度。
5. **前端仍由同事负责**：本方负责后端和清晰的协议适配说明，不将前端源码混入交付包。

姓名字段示例通常增加约25–50 UTF-8字节/条：50条约1.25–2.5 KB，1,000条约25–50 KB，10,000条约250–500 KB。只是按常见姓名、字段和JSON格式估算，未计压缩，也不是性能实测。解析和客户端内存开销同样需验证。任何压测仍须单独获得用户授权。

## 七、实施前仍需决定

- **姓名时间语义**：当时姓名快照还是当前目录姓名？历史报价、旧报价缺名、目录恢复、人员改名及Unrefer如何保持一致。用户尚未拍板，不自动迁移历史数据。
- **行情字段约定**：沿用既有命名规范确定价格簿对应的本方姓名字段，不复用表示对手的`TraderName`。字段最终名称尚未确认。
- **无法解析时的UI呈现**：统一空值/未知用户策略，避免重新展示内部ID；不要把当前各页面不一致的兜底当成已批准新契约。
- **刷新细节**：周期、启动就绪、停用/删除用户和刷新失败处理，及姓名变化是否触发已有视图刷新。

## 八、恢复实施时的验证清单

- 实际STC目录→QuoteSvr→真实网关→客户端DTO/缓存/页面；不得手工补字段绕过上游。
- 手工创建、clone、QT单聊/群路由、确认/修改、Refer/Unrefer、重启恢复；姓名必须属于实际owner。
- 普通报价、今日/历史查询、行情价格簿及展开明细、通知初始快照和增量推送；包括同档多owner。
- 旧记录无姓名、用户不存在、姓名空但登录名存在、停用用户、人员改名、目录刷新失败与恢复。
- 非法请求不能设置ownerUserName，权限和业务去重仍只依据ID。
- 证实创建/响应关键路径没有逐报价数据库查询，保存报文大小与普通功能请求耗时证据；不擅自运行压力测试。
- 前端由同事验证；缺环境或数据的项标明未验，不能将组件测试或patch可应用说成验收通过。
