# QuoteSvr、网关与通知同步：本机主备切换实测

日期：2026-11-04。基线：integration/ficc-client-convergence，dc570201。

## 结论及更正

正确配置RegType=2后，备用QuoteSvr自动接管，同一网关客户端登录恢复读取，NotificationSvr自动重新同步。基础进程故障切换链路成立，但不能据此宣布完整高可用已经验收。本轮只调查、测试、记录，没有修改产品代码；剩余缺陷先讨论。

更正此前审查：不能只看JdbcStore写锁就推断备用无法等待。实际启动顺序是：

QuoteSvr.main → ServerWrapper → ServerGwWrapper → ZkCluster选主 → 获选回调 → ServerShell/BBox → QuoteResource → 数据库写锁。

RegType=2时，未获选的备用尚未初始化QuoteResource，不会争抢数据库写锁。获选后才加载资料与报价工作集。原本机RegType=1是全部实例模式，不是主备模式。

## 实测范围

实际本机ZK、GW、PostgreSQL、BaseSvr、QuoteSvr、NotificationSvr；使用部署中的原有JAR，不模拟服务响应。主端口28680、临时备用28690，共用业务库、工作目录独立。一个网关客户端、小样本请求，没有并发压测。备用有独立低内存/超时看门狗。

## 待讨论问题

1. **备用启动入口误报异常。** ficc.quote.Main第13行立即调用Server.getServer().getStatus()；正常备用尚无Server，实测抛NullPointerException。ZK线程仍活着，故本次能接管，但主线程异常会误导监控。建议明确等待备用、初始化、就绪、失败，不可简单吞掉异常。
2. **初始化失败仍可能注册为就绪。** 本次RegType1下数据库写锁失败后仍创建Stat1。ServerGwWrapper捕获初始化异常未向上传递，ZkCluster继续登记。建议业务初始化成功才登记就绪，失败撤销注册。涉及同事共享框架，须确认范围后修改。
3. **配置必须一致。** 模式1调用方监听子节点；模式2调用方监听固定节点数据。升主创建Stat0再更新Stat1，混合配置会漏掉就绪变化。建议部署生成时校验所有调用方，而非只改QuoteSvr。
4. **本机启动脚本不适合备用健康判断。** 正常备用不监听业务端口，而脚本等端口超时会终止进程。本次用了独立受控启动器；生产进程管理仍需确认。
5. **桌面自动重开视图未验收。** 探针主动重开不等于STP页面自动恢复已通过。还应让真实页面不操作，重复切换，验证列表和增量恢复。

不建议先扩大JVM或去掉写锁：正确主备不会让等待中的备用抢锁；本次问题集中在生命周期、就绪登记和配置一致性。
