# QuoteSvr / NotificationSvr 长期运行与高可用审查

日期：2026-11-04。基线：`integration/ficc-client-convergence`，`89ab0aa7`。

后续更正（2026-11-04）：实施时发现价格簿虽然从输出中剔除失效报价，但quotesBySecurity仍持有终态对象；早期关于价格簿已移除无效报价的描述不涵盖该内部引用。本轮已修复该引用和日终工作集释放，实际功能与网关验证范围见[实施备忘](../task-memos/2026-11-04.md#日终释放历史报价工作集实施与本机验证)。以下保留原只读审查基线，不代表长稳及高可用问题均已解决。

范围：当前 Common、QuoteSvr、NotificationSvr 源码及源码运行配置。只读调查，未修改产品、未重启服务、未启动压力或长时间运行测试；不代表 QA 当前部署版本已逐一比对，也不代表高可用验收通过。

## 结论

确实有长期运行风险，主要是业务对象没有退出内存的生命周期，并非已证明存在 JDBC 连接不断泄漏。NotificationSvr 另有明确的分页重复调用及过期缓存清理遗漏。

已有单写保护、数据库重连、快照恢复、增量序列校验和退避重试，但目前更接近“单活服务故障后恢复”，不能直接称为自动主备或双活。单写锁保障同一数据库内的写入互斥，不负责备用实例自动接管。

## 已确认问题

### 1. 高优先级：所有报价长期留在两个服务的内存中

- QuoteSvr：`QuoteColumns.readSql()`（78–84行）读取整个 `quotes` 表，没有按状态或日期限制；`QuoteService` 构造、数据库恢复均将这些报价放入 `quotes` Map。
- 删除只把状态改成 `DELETED`（QuoteService约550行）；日终到期只更新报价并 `quotes.put`（约819行）。没有对应的历史报价淘汰流程。行情价格簿会移除无效报价，但主报价 Map 仍保留。
- 内部状态同步 `stateRecords()`（约1456行）把整个主报价集合提供给 NotificationSvr。后者 `replaceQuotes()` 加载全部，`quoteMessage()`（约227行）也只覆盖/增加报价，不按终态移出。
- 这里是“每个 quoteId 的最新记录”，不是把该报价的所有审计版本都放进内存；但新增 quoteId 随运行日数累积。假设每天新增一万笔，一百天可累计一百万笔最新记录，日终撤销并不会释放这些对象，重启仍会从数据库全部加载回来。
- 后果：常驻堆、重启恢复时间、内部同步规模持续增长。NotificationSvr 的 `recompute()` 还会遍历全部报价筛选 ACTIVE，旧数据越多，处理新事件的成本也会上升。
- 建议：先明确在线工作集，历史仍保留在数据库；对旧报价的按ID查询、Unrefer及幂等重试保留按需读库能力，再从实时内存和恢复快照中淘汰不再需要的记录。不能简单删除数据库历史，也不能只删内存却遗漏旧报价操作链路。

### 2. 高优先级：失效提醒也一直保留，并可随报价版本增加

文件：`NotificationService.java`。

- 启动和数据库恢复都执行 `SELECT payload FROM notifications`，包括 inactive 记录（52、192行）。
- `putDesired()`（551–556行）的通知ID包含相关报价的 revision 摘要；符合这一构造路径的报价版本变化，可以形成新的通知ID。
- 旧提醒仅改成 `active=false`，随后仍通过 `notifications.putAll(changes)` 留在 Map（519–534行），并没有移出。
- 因此即便活跃提醒只有几条，内存仍可能保留大量过去的提醒。循环、重新计算和启动加载也会受到影响。
- 建议：区分在线活跃提醒与历史/已读留存；先核对旧提醒查询及再次命中的规则，再设计非活跃记录退出内存，不能直接删已读状态或历史。

### 3. 中优先级：NotificationSvr 分页处理重复，且过期快照没有定时释放

文件：`NotificationService.java`，约698–702、1193–1260行。

```java
if (request.getString("cursor") != null)
    data = continuePage(user, sid, topic, request.getString("cursor"));
if (request.getString("cursor") != null)
    data = continuePage(user, sid, topic, request.getString("cursor"));
else data = dispatch(op, user, sid, topic, request);
```

- 同一个续页请求执行两次。还有下一页时，会生成两个新的游标，第一次结果被丢弃。
- 原游标未消费删除；过期清理只在 `pageResult()` 需要创建下一页游标时执行。心跳并不清理 `pages`；如果之后没有新的多页查询且登录会话仍有效，过期或已读完的快照仍被引用。
- `pages` 有64条上限，所以不是条目无限增长；但没有总字节预算，`page()` 又会先复制整份结果再检查游标容量。正常翻页也可能更早触发游标数量上限。
- 同一结果的多个游标共享 `rows`，不能把两个游标说成两次全量深拷贝；全量复制发生在新的第一页请求。
- 建议：去掉重复执行；明确完成/放弃/超时的释放流程，并在创建大快照前检查容量。若需要支持续页请求重试，应同时保留明确的重试语义，不能随意改成一次性读取。

### 4. 中优先级：NotificationSvr 异常停止时可能跳过后续资源释放

文件：`NotificationResource.stop()`（397–427行）。

- `bondSearch.stop()` 或 `service.refs.close()` 抛异常，会跳过后续 `store.close()` 和 `super.stop()`。
- `awaitTermination(4秒)` 的返回值未检查，后台任务还没退出时也可能继续关闭数据库。
- 这是异常停止/同JVM重新加载时的条件性资源风险，不是已证明每个业务请求都泄漏连接。进程彻底退出后，操作系统会释放其资源。
- 建议：停机时按顺序尝试释放全部已创建资源，汇总异常；明确后台线程未退出时的处置。QuoteSvr 的日终线程超时则主动拒绝关闭数据库，需结合进程管理规则单独验收，不能把两者视为同一种遗漏。

## 高可用：已有能力与缺口

| 事项 | 当前代码行为 | 评价 |
|---|---|---|
| 防止同库双写 | JdbcStore构造时获取 `schema + 服务名 + .writer` 的 PostgreSQL advisory lock；第二实例拿不到就抛异常（82–88行） | 有单写保护；不是整库独占，QuoteSvr与NotificationSvr的锁名不同 |
| 自动备用接管 | 未看到服务内的等待主锁、备用状态及自动升主流程 | 不能仅启动两个同名实例就认为具备自动主备；外部进程管理是否负责重启备用，需部署验证 |
| 数据库连接失效 | ensureConnected重建连接、重新获取写锁、校验epoch；上层按connectionGeneration重新加载状态 | 旧的“连接断后永远不能恢复”问题已修复，不能再按旧代码评价 |
| Notification同步恢复 | 有界128消息队列、连接代次、epoch/sequence校验、断序恢复、2秒到30秒退避、未就绪返回1009 | 有恢复设计，不是无保护的固定2秒重试 |
| QuoteSvr内部快照 | 引用固定报价对象集合、按页序列化；消费旧StateCursor，同一调用范围重建会清旧快照，64条上限与定时过期 | 已不同于旧的全量JSON深拷贝风暴；仍受主报价集合总量及跨会话残留快照影响，条数上限不是内存字节上限 |
| 实例切换 | view、cursor等上下文在本实例内存里；数据库恢复会重置视图，通知源变化会恢复 | 客户端必须重开流/视图，不能将旧游标发送到任意实例；未完成真实网关切换验收 |
| 业务卡住但连接还活着 | Notification tick主要检查 source.isOnline、连接代次及收到的序列；未见独立的上游业务心跳超时判定 | 不足以证明“TCP在线但QuoteSvr业务线程卡住”能及时被发现；底层传输心跳不等于业务数据新鲜 |

特别说明：共享数据库上的会话锁不能替代数据库集群自身的单主保障。如果部署存在两个独立可写数据库端点，需要由数据库和部署层保证故障切换不会双主，不能仅依靠本代码中的锁名。

## 其他核对结果

- JdbcStore常规查询的 Statement、PreparedStatement、ResultSet使用try-with-resources，当前未发现这部分每次调用遗留资源的直接证据。
- CalSvr计算线程池队列有界，价格簿移除无效报价时调用forget清理计算缓存；不能把所有Map都视为泄漏。
- 两服务都接了身份失效回调：注销/更新或LoginSvr连接变化可清理对应streams，Notification还清理pages。因此“会话完全没有清理”不成立。不过缺乏独立空闲回收；客户端异常退出后若注销事件未送达，是否回收依赖实际LoginSvr行为，尚待验证。
- 两服务的viewId历史使用集合在会话内只增不减，当前限制的是同时打开的view数量，不是已用ID总量。长期同会话反复开关页面有增长风险，优先级低于报价及提醒正文留存。
- events、requests、notification_reads等留存表未见产品内自动归档/清理任务。它们有审计、幂等和已读语义，不能贸然删除；需定义保留窗口及外部维护责任。磁盘增长是容量治理问题，不等同于Java堆泄漏。

## 建议顺序与后续验收

1. 先修明确且范围小的重复分页和释放遗漏，补对应回归。
2. 确定在线数据保留边界，再处理报价和失效提醒的内存增长；历史仍可查询，旧报价仍可按业务规则操作。
3. 如果要求自动高可用，先选定单活自动接管方案，明确谁负责选主、谁负责启动/重试备用、业务未就绪时网关如何处理。不要仅添加ZK注册就宣称完成HA。
4. 经用户批准后做分阶段测试：连续增删/日终/提醒更新后的Full GC存活堆趋势；分页中断与结束释放；客户端异常退出；数据库断连恢复；QuoteSvr宕机与实例切换；上游业务线程卡住但连接仍在。

本次没有启动这些测试，不给出可运行多少天、多少内存或接管几秒的推测数字。此前memo记载的本机数据库终止连接测试只是历史证据，不替代本轮长期运行及QA切换验收。
