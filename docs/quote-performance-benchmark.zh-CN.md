# QuoteSvr 典型业务性能基准

本工具是显式运行的服务端基准，不会由 Maven test 自动启动。当前获准的起始负载为 **5,000 条报价、10 个用户、每用户 4 个 view**：2 个报价 view、1 个 BEST 行情 view、1 个 DEPTH 行情 view，pageSize=50。没有 UI，不会创建或渲染 5,000 行网格。

## 验收目标与扩展路径

正式目标：在上述起始负载下，**STC 客户端应用筛选条件 → GW → 服务 → GW → 客户端应用结果行的 p95 < 100 ms**。切换条件时应包含关闭旧 view、新建 view 和客户端处理，不能只取一次 RPC 的时间。首次登录、BaseSvr 冷启动和造数单独报告，不混入稳态结果，也不隐去冷启动耗时。

当前服务端基准的 `PASS` 只表示全部场景和正确性检查完成。报告固定标记 `endToEndAcceptance=NOT_MEASURED`，不代表端到端验收通过。后续实测还需记录 UI 线程等待、GW 往返、反序列化、结果应用；屏幕绘制完成须单独定义与测量。推送应采用同一测量时钟关联修改请求和接收端应用完成，不能直接相减不同机器的墙钟时间。

起始测量保持每用户最多一个在途业务操作、每页 50 行；报告必须写明操作频率、条件选择率、报价分布、活跃 view 数和更新频率。只有报价数／用户数而没有请求速率，不能定义容量。更高压力不自动运行。

| 资源或设计 | 当前实现／限制 | 后续扩展的验证方式 |
|---|---|---|
| CPU 与请求线程 | 报价页响应转换移到共享锁外，由现有请求线程并行完成；匹配、排序、view 状态提交仍在锁内 | 同一负载比较 CPU、锁持有时间与队列等待；不能宣称整个查询已并行 |
| JVM 堆 | 首轮仍为 128 MB，只构造所需页的报价 JSON；记录 GC 与分配压力 | 经确认后单独增加堆，比较 GC 暂停和 p95；不能靠堆掩盖全量序列化 |
| 增量更新 | 报价按 ID＋revision 保存匹配状态；更新只处理受影响报价，行情只重算受影响债券 | 混合更新场景仍须优化、实测；当前写事务和推送构建仍串行 |
| 查询并行的下一阶段 | 尚未实现：从一致的报价／基础资料／筛选组快照计算，提交 view 时核对版本 | 必须覆盖查询期间更新、关闭、条件变更、推送先于应答等竞态；不能直接删 synchronized |
| 更高更新吞吐 | 尚未实现：按 stream/view 分区的有界任务队列，保证同一流序号有序 | 对慢消费者设置背压／重建语义；记录排队和客户端收到时间 |
| 多实例 | 当前数据库有单写者约束，不能直接复制写服务扩容 | 需要单独设计只读副本或业务分区，不属于增加 JVM 参数即可实现的能力 |

先减小单次工作量，再在固定数据和请求模式下改变一个资源参数。现阶段不承诺增加线程／CPU 后线性扩展，也没有完成正式端到端验收。

## 运行

在仓库根目录使用：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File iteration1/scripts/benchmark-quotesvr.ps1
```

默认读取被 Git 忽略的 `iteration1/runtime/quotesvr.local.properties`，仅允许 localhost／127.0.0.1 PostgreSQL。需要其它本机配置时使用 `-Config <文件路径>`。配置内容不会写入报告。工具创建独立 `ficc_bench_<随机后缀>` schema，正常退出或内部预算退出时只删除本次 schema。外部强制结束时可能保留它，报告会注明清理未确认，不触碰产品 schema。

- `-BuildOnly`：离线 Maven 编译及少量单元测试，不启动基准。
- `-SkipBuild`：仅当源码指纹与上次成功编译一致时运行。
- `-Distribution spread`（默认）：5,000 报价分布在 100 债券，选择一券约命中 1%。
- `-Distribution concentrated`：所有初始报价集中在同一券，用于另一次获准的价格簿压力检查；本次未运行。此分布的单券筛选不再是 1% 选择率。

固定数据种子为 20260929；报价归属、代码、价格与基础属性按确定规则生成；交易日使用运行当天以符合服务校验。每次数据库、请求 ID、view ID 与源代码信息记入报告。真实 BaseSvr／CRM／GW 不参与；直接调用现有 QuoteSvr handler，报价修改和筛选组保存使用实际 PostgreSQL。

## 场景

| ID | 内容 | 测量 |
|---|---|---|
| S01 | 打开宽条件、单券、地区＋债券类型＋评级＋价格区间 view | open 请求时延，返回第一页及 totalCount |
| S02 | 关闭旧 view 并切换条件 | close/open 分别计时，不把单步时延冒充整个切换周期 |
| S03 | 修改仍匹配的报价数量 | update 应答与首／末私有 view 发布回调时延 |
| S04 | 报价进入／退出价格筛选 | upsert/remove、totalCount 与时延 |
| S05 | 最佳报价换券，再移回；目标券初始为空 | 旧／新券价格簿重建、最后一条移除 |
| S06 | 10 个用户同时请求报价页，部分条件共享、部分不同 | 锁等待、总时延、测量窗口吞吐 |
| S07 | 5 个用户关闭／新建 view，另 5 个修改报价 | 创建删除与增量推送争用；最多 40 活动 view |
| S08 | 保存、修改、删除被 view 引用的筛选组 | 持久化、重算、预期 RESET_REQUIRED；本场景单周期 |
| S09 | 5 个用户查询后续页，另 5 个修改报价 | 分页与更新争用，完成后检查 view 清理 |

顺序场景 1 次预热、3 次测量；并发场景每周期 10 个调用者，S07 某些调用者执行 close/open 两个请求。预热不计入请求样本。每场景后用不调用 FilterEngine／QuoteMatcher 的固定条件 oracle 检查 ID 集合和总数；更完整的报文／价格档位正确性由 IncrementalViewSmoke 回归负责。功能断言数量不等于独立业务场景数量。

## 保护和报告口径

- 单 JVM、最多 128 MB Java 堆、限制到 2 个逻辑 CPU；操作系统互斥锁防止同一工具重叠运行。
- **15 秒独立进程 watchdog**，包含 JVM 启动、造数、场景测量和清理。进程内 12 秒工作预算为清理预留时间。编译不计入负载运行时限。
- 不自动增加报价／用户／view 数，不自动加时、循环重跑或切换集中分布。
- 每轮输出目录：`iteration1/runtime/quote-benchmarks/<时间-标识>/`。保留 `report.zh-CN.md`、`report.json`、原始 `result.json` 和控制台日志。构建失败也有报告。
- 报告含分场景／接口 p50、p95、p99、max、错误数、锁等待、查询阶段、增量匹配、价格簿、发布编码、CPU、GC、采样堆占用及清理状态。发布回调是进程内编码出口，**不代表客户端收到或显示完成**。
- 场景吞吐含测试准备与同步成本，不是最大持续吞吐；阶段时间可能嵌套，不可简单相加。内存池峰值之和不是同时堆占用，更不是进程 RSS。
- 目前样本很少，顺序场景 p95／p99 常等于最大值。100 ms 是待验证的 p95 目标，不是保证；两核／128 MB 限制会影响结果，不能直接外推生产容量。
- 超时／预算不足报告 `INCOMPLETE_TIME_BUDGET` 或 `WATCHDOG_TIMEOUT`；未测量场景显式标注，不判通过。

## 2026-09-29 报价页优化后的诊断结果

运行目录：`iteration1/runtime/quote-benchmarks/20260929-145600-8059e2/`。仍为 5,000／10／4、2 个逻辑 CPU、128 MB 堆、15 秒 watchdog。没有提高压力；S01–S09 全部完成，隔离 schema 已清理。

代码变化：报价 view 用 ID＋revision 维护成员，不为全部匹配报价计算 JSON 哈希。分页只捕获当前页的稳定报价版本和 stream sequence，在锁外构造该页的 JSON 应答。写入仍以新 QuoteRecord 替换旧版本，不能原地修改已发布记录。行情 view 的全量分页路径尚未采用这一优化。

回归验证包含：报价／行情增量结果与全查询一致、筛选进入退出、换券、筛选组变更、关闭并发，以及新增的分页快照在更新后保持旧版本、编码不占用服务锁、他人机构／联系人字段脱敏不修改存储记录。构建与回归不等于重新进行了压力测试。
