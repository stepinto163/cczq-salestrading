二、为什么修改，最终行为是什么
1. 原精确报价和“新报价”先创建待确认记录，再调用确认；第二步失败会留下待确认。本次在现有ficc.quote.create增加可选confirmOnCreate参数，true时按正式报价规则校验并原子创建ACTIVE报价，不再另发确认请求。
2. 原子性以单条报价为单位，不是整批全部成功或全部失败。单条的报价、同业务键旧报价替换、历史、事件及回执一起提交；失败则回滚。批量仍允许部分成功，失败行留在客户端输入页面供修改。
3. 成功行返回quoteId、revision、status=ACTIVE及Code；失败行沿用Code、Msg、error.type和error.field，包含确认校验失败的原因。客户端不能把顶层Code=0000当成所有行成功，不能在通信超时后换requestId重复创建。
4. 不传confirmOnCreate或传false仍创建PENDING_CONFIRM；QT接入不接受该开关，继续人工确认。已有待确认记录不自动转换，不改变已有确认接口。
5. 只有券、方向、交易日期、清算速度必填；机构、交易员、价格、报量均非必填。已填写的机构/交易员仍须匹配有效CRM信息。报量填写时必须大于0；空值不等于0。
6. “新报价”窗口原来忽略数字转换失败，将空价格/报量变成0，引发报量校验失败。本次保留null，并补充真实WPF窗口的空值转换检查；不把业务规则改为价量必填。

三、供QA AI执行的合并步骤
1. 先读取本说明、changes.json、manifest.json。确认QA已经合并昨天的基础包；没有合并时，先按完整源码对比完成基础合并，不能直接套用增量补丁。
2. patches目录分别提供Common、QuoteSvr、stc-client的增量补丁，路径相对于各组件仓库根目录；基线分别为昨天后端5d009de及客户端613ee2947。变更清单列明新增/修改文件，本次没有删除文件。
3. 在各自QA分支先检查git状态并保护已有改动，执行git apply --check <补丁路径>。确认可应用后执行git apply <补丁路径>；存在冲突时用sources中的最终文件逐项人工/AI比较合并。不要整目录强制覆盖，不要删除包中未提供的QA文件，不要执行reset --hard。
4. 客户端目标是同事STC/STP仓库，不是另一套iteration1/stc-client。同步Gateway契约、GatewayQuoteService、新报价窗口及测试文件。
5. 构建顺序：现有parent/Common → QuoteSvr → 同事客户端。Common新增请求/结果字段必须进入QuoteSvr实际加载的依赖目录，不能仅替换QuoteSvr主JAR。使用现有Jenkins/Salt及STP流水线；保留QA环境地址、共享$ATS_ROOT/control引用和许可证管理方式，不复制开发机连接配置。
6. 后端先部署并确认就绪，再更新客户端。旧服务端不识别confirmOnCreate时应明确报错，不通过删除参数退回“先创建再确认”。NotificationSvr/BaseSvr本次没有新增源码改动。
7. 保留STP的Ficc.ReferenceSyncEnabled=true、Ficc.BaseService=BaseSvr及既有基础数据插件。运行环境要求.NET Framework 4.7.2或兼容更高版本，沿用昨天部署前提。
