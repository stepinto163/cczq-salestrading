# 历史报价查询与页码分页

## 业务口径

`ficc.quote.history.search` 查询指定日期范围内，每条报价每天最后一次操作后的状态。先选最后版本，再判断正式报价状态、权限和筛选条件，不能因旧版本符合条件而返回旧价格。相同时刻以 revision 较大者为准。行 tradeDate 取 operationTime 的日期部分，不是 quote.tradeDate。

已确认正式报价按现有共享规则可见；未确认输入及直接丢弃的草稿不进入历史。ownerScope 默认 VISIBLE，MINE 限定本人。债券属性、关注债券和筛选分组使用公共 QuoteMatcher，基础资料采用查询时的值。

## 分页协议

2026-10-21 起，历史报价筛选使用页码分页，不再使用游标：

```json
{"requestId":"history-1","fromDate":"2026-10-01","toDate":"2026-10-20","pageNumber":2,"pageSize":50,"ownerScope":"VISIBLE","filter":{"market":"RATE"}}
```

成功响应 Data：

```json
{"pageNumber":2,"pageSize":50,"totalCount":51,"hasMore":false,"rows":[{"tradeDate":"2026-10-20","quote":{"quoteId":"Q-051","securityId":"240210.IB","status":"ACTIVE"},"reference":{"securityId":"240210.IB","securityName":"24国开10"}}]}
```

上例共 51 条，第 2 页包含最后 1 条；行内 quote/reference 字段为节选。

- pageNumber 默认 1，最小 1；pageSize 默认 50，范围 1–1000。
- 每次请求携带完整条件，可直接跳页。totalCount 是筛选后的全部匹配数量。
- 越界页返回空 rows，保留 totalCount，hasMore=false；参数非法返回 1001。
- 不接受 cursor/limit，不返回 nextCursor；移除原 10,000 条结果缓存上限。
- 客户端增加与今日报价一致的分页控件；日期、文本及侧栏条件变化回到第 1 页。客户端不再对已分页结果二次过滤，Bid/Ofr 计数标明“本页”。

这是无状态页码查询：同一次请求的计数与数据基于同一个数据库查询快照，但不同页之间不冻结历史记录。并发新增/修改历史可能让行跨页移动；需要查看最新结果时重新查询。单笔报价变更历史 history.query 的 snapshotRevision 机制不受影响。

## 服务端处理

1. PostgreSQL 按日期缩小范围，选出每日最后版本，再应用正式状态和权限。已有 history_owner_time_idx、history_time_idx 索引由 PgStore 初始化维护。
2. 仅日期/归属筛选时，SQL 在同一语句中计算总数并 LIMIT/OFFSET，只返回本页。
3. 仅报价自身条件（价格、数量、方向、计价方式、清算速度及标志等支持的运算符）时，将条件下推到每日最后版本之后，在同一SQL中筛选、计数、分页；只向Java返回本页。
4. 市场/DM债券条件复用原引擎的命中券集；关注债券和筛选分组按原来的并集/交集关系形成必要券集。将券集、MINE和可支持的报价条件下推到每日最后版本之后，缩小数据库返回范围；剩余条件继续执行公共QuoteMatcher。空券集直接返回空页；未支持的同字段OR条件整组不下推，避免误排除。
5. 复杂筛选仍以128行批次读取预筛后的快照、准确计数，仅保留本页。综合搜索、当前期限/估值差等依赖当前资料的条件保留原有匹配口径；没有把当前资料改成历史快照资料。
6. 排序沿用每日首次操作时间升序，再按操作日期和 quoteId 排序，保证同一数据集顺序稳定。

数据库仍需按日期选取每日最后版本；非选择性条件、复杂条件、准确计数及深页OFFSET仍有成本。此次主要减少跨数据库传输和Java反序列化，不宣称已消除海量历史的数据库扫描成本。

新增INFO日志HISTORY_QUERY包含user、mode、page、transferredRows、candidateSecurities、totalCount、returnedRows、elapsedMillis。transferredRows是数据库实际返回到服务的快照数，不是数据库内部扫描行数。准备期间资料版本变化返回NOT_READY，避免混用两版候选券集与匹配器。

2026-11-03验证：Common 103项通过、1项既有跳过；QuoteSvr 16项通过；原历史数据库功能检查188项、新差分检查486项通过。新检查用原路径与优化路径比较原始快照内容、顺序、计数和分页，包含空价量、零值、边界、同字段OR、旧版本不能复活、归属变化、缺资料及真实原版DM引擎匹配。功能样本中选择券集使传输由11条降到4条；简单条件页大小2时只传2条。此为功能数据量检查，不是耗时性能结论。

### 已确认的瓶颈

1. 每个场景仍扫描100000条操作记录，经过窗口计算与DISTINCT选出20000条每日最后版本，再匹配候选。券集只命中200条，也要付出前面的全量日期范围处理成本。
2. EXPLAIN显示历史排序落盘：在10万候选广命中场景，两次历史排序分别约48904KB和37080KB；最终20000行展示排序约8056KB。临时块统计是执行节点累计值，不能逐节点相加。当前SQL窗口分组顺序是quote_id/date，而DISTINCT排序为date/quote_id/time/revision，存在重复排序优化空间。
3. JSON券集约1.2MB；规划器对jsonb_array_elements_text估计100行，实际100000行。历史有效快照表达式也被低估（部分节点估计500，实际100000）。大券集确有额外成本，但本轮主要成本仍在历史版本选择及排序，临时表没有整体收益，不能据此直接换实现。
4. 广命中时现实现仍向Java传20000条并计数，最终客户端只要50条。SQL分页原型降至约860ms，但它没有消除历史排序，因此不是完整的大规模方案。

### 建议先实施的设计（待讨论，尚未修改生产代码）

1. **先优化选版本SQL，保留现表。** 排序阶段只携带event_id、quote_id、日期、时间、revision等窄列；选完每日最后event_id后再关联读取JSON。评估统一窗口与DISTINCT排序键，减少重复排序；必须保持first_operation、最后版本、状态/权限及分页顺序语义。
2. **纯债券条件走数据库计数分页。** 将条件分类明确化：原引擎候选能完整表达时，直接SQL计数/分页；含报价条件的分组、综合文本、需要现有匹配器的条件仍走安全剩余匹配。不能仅凭有候选ID就认定筛选完整。

## 2026-11-03后续决定：采用每日报价历史表并完成百万审计重评

### 最终实现

- 原history保留每次操作，用于变更历史与审计；新增quote_history_daily，主键(operation_date,quote_id)，每日报价最终快照，不以securityId去重。

- 启动自动分批回填旧数据并原子安装触发器、索引、版本标记；失败完整回滚并阻止启动；后续启动只校验，不扫描重建全量历史。操作日期与上海时区必须一致，异常旧数据需要纠正来源，不能静默产生错误日快照。表结构/部署说明在QuoteSvr deployment/quote-storage.zh-CN.md。

### 2026-11-03 规模更正：一百万条独立报价，不是一百万条审计

用户明确要求“1000,000 quotes not audit record”，此前十万报价的成绩不能代表此目标。本轮固定100万不同quoteId、10万券、每券10条报价、20自然日、每条报价初始一条事件；每日查询表实际count(*)为100万行，不把审计事件数混称报价数。仍为1客户端，合成候选券集合，不含DM实际匹配、网关及界面。

1. 原每日表实现（cf12d75d）：小集合查询4.01ms；10万券广命中100万报价时SQL8秒超时，阶段中止并清理schema。说明之前10万报价测试不足以证明百万报价可用。
2. 定位：EXPLAIN显示JSON候选展开估计100行，而实际10万券，选择嵌套循环＋索引探测；不是数据量只有100条。改为JDBC text[]绑定及ANY，使规划器可见真实数组，并选择并行扫描。SQL仍绑定参数，不拼券值；不改同事BondSearch、筛选语义或前端协议。
3. 重复执行保障：Common JdbcStore仅对512项及以上String[]参数关闭该语句的服务端预编译，避免后续通用计划失去数组规模信息；普通参数保持原行为，JDBC参数绑定不变。PostgreSQL现有依赖调整为编译可见以使用PGStatement，驱动版本和部署依赖未增加。未修改任何公共API签名。
4. 结果：中间仅数组版本广命中3.49秒；最终增加重复执行保障后10次广命中中位2.80秒、范围2.56–3.11秒。两次运行缓存/波动不同，不能把3.49→2.80秒全部归因于保障措施；已验证服务端预编译计数为0。

### 2026-11-03 后续优化评估（仅评估，未改实现/未再压测）

用户询问是否还有进一步提升空间。复核最终百万报价SQL及保存的EXPLAIN：当前CTE先生成全部匹配键，再供精确计数与排序分页重复扫描，完整JSON已只读取最终页；状态/确认时间仍从snapshot JSON读取。最终广命中计划仍估计14923行，实际结果100万，说明候选列表修正后选择率估算仍不准确。保存的是EXPLAIN估算，不是EXPLAIN ANALYZE/BUFFERS；不能把2.80秒按阶段分摊，不能宣称已确认磁盘排序或具体耗时占比。

建议按以下顺序小步验证：
1. 在同一SQL语句/快照中让精确计数与页数据分别选择计划，避免强制物化并遍历全部匹配键后才取50条；评估CTE NOT MATERIALIZED或等价改写。它可能重复过滤，对选择性高的请求未必更快，需与原SQL差分和实测。
2. 配合正式报价条件的部分覆盖索引：为计数提供券/日期等窄索引，为分页提供稳定排序键及必要过滤字段，尽量避免扫描宽JSON。可以先不新增业务字段。索引大小、写入成本与刚回填/持续写入后visibility map状态必须同时评估，不能假设index-only必然无需回表。
3. 核对状态/确认条件表达式及相关列统计，改善14923对100万的低估；以实际计划验证，不把新增统计当作必然提速。
4. 保持现有页码/精确总数/可见性规则，不擅自改游标、近似计数或缓存。深OFFSET和复杂残余筛选另评；本轮1500页不是百万行尾页。
