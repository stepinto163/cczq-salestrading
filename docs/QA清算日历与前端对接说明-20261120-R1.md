# 20261120-R1：清算解析节假日与 +N 修复

本包只含 ParserSvr、QuoteSvr 后端源码、补丁及测试；不含客户端、STC共享基础包修改，无新配置或数据库迁移。

## 修复原因

上一版20261119-R3在QuoteSvr用自然日加一计算“明日”，未使用交易日历；解析及转换还把+3等速度降成+1。

已核对基础包：WeekDateSettlement.calTod0Tod1AndAll2只扫描+0/+1；getDateBySettlementType能按BaseSvrClient订阅的CNY_CIB日历计算“明天”。ParserSvr.BaseStream已启用isLoadAllHoliday并订阅日历，QuoteSvr没有此订阅。因此由ParserSvr复用基础包计算交易日，QuoteSvr只传递结果。

## 最终行为

- 文本提取保留+0至+12；“明+N”“明天+N”同义，明加一等中文单数词也支持。超出范围明确失败，不能默认T+1。
- 每次识别使用新的WeekDateSettlement和上海基准日期，复用日历求交易日，保留独立的清算速度N。不复制共享库、不自行写节假日算法。
- 日历未加载或不覆盖日期时明确报错；无效日期不自动滚到下一月。
- Parser原有tradeDay返回yyyy-MM-dd，settlementDay返回+N；普通识别响应也增加tradeDate。
- QuoteSvr识别接口tradeDate返回完整交易日。当日+0/+1仍为旧编码1/2；远期或其他速度用已有MM.dd+N形式。旧编码3/4的语义没有改成正式报价T+2/T+3。
- 升级不完整、旧Parser仍未给出远期日期时，QuoteSvr明确提示升级，不猜测自然日。

## 合并与部署

1. 按manifest基线合并两个组件补丁；完整源码仅用于核对，勿覆盖QA其他修改。
2. QuoteSvr仍依赖此前R3的Common（IdentifyQuote已有tradeDate），本包不变更Common。
3. 两服务协调升级，建议先ParserSvr再QuoteSvr；不要只升级一个。Jenkins/Salt配置保持原样。
4. 前端同事按下面说明修复+N解析。本包不能标记为前后端整体验收通过。
